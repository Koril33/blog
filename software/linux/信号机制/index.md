## 前言

Signal 是 Linux 向进程传递异步事件的一种通知机制。它可以通知进程退出、暂定、继续运行，或者处理某个特殊的事件。

信号的概念源自 Unix 的早期设计者（Thompson、Ritchie 等），由 BSD 和 POSIX 完善，Linux 实现并继承了这套机制。

---

## 概念

以后端服务为例，假设在某台 Linux 上部署了一个后端服务（Python Flask、Spring Boot、NodeJS 之类的），管理员（systemd、docker、或者别的管理进程）想要给后端服务一个信号（服务停止、重启，或者其他操作），就可以通过 signal 机制传递这个信号。

signal 的重要性在于，它可以让其他进程在不直接调用目标程序内部函数的情况下，向目标程序传递信号，至于目标程序收到了这个信号会如何处置，则取决于信号的默认行为以及目标程序的开发人员是否有编写相应信号的处理逻辑。

---

## 信号类型

manpages 中标准的 signal 类型有几十种，但实际开发运维过程中较为常见的有以下几种：

| 信号 | 用途 | 默认行为 |
| --- | --- | --- |
| SIGTERM(15) | kill PID、systemd 停止服务 | 终止进程 |
| SIGKILL(9) | kill -9 PID、强制清理进程 | 立即终止 |
| SIGINT(2) | 终端按下 Ctrl+C | 终止进程 |
| SIGHUP(1) | 终端断开 | 终止进程 |
| SIGQUIT(3) | 终端按下 Ctrl + \ | 通常终止并产生 core dump |
| SIGHLD | 子进程退出、暂停或继续 | 默认忽略信号，但父进程仍需正确处理子进程状态 |
| SIGPIPE(13) | 向已关闭读取端的管道写入数据 | 通常终止进程 |
| SIGTSTP(20) | 终端按下 Ctrl+Z | 暂停（挂起）进程 |

这些是 Linux/POSIX 信号常见的用法和默认行为，具体的服务可以捕获并且改变部分信号的处理方式。

---

## SIGTERM、SIGKILL、SIGINT

SIGTERM 表示正常退出，就像是在关闭计算机前，你可能会选择保存文件，关闭运行中的程序，确保没有什么遗留事项后再关闭计算机。

SIGKILL 则是不由分说的直接终止，SIGTERM 可以被应用程序捕获，程序员可以在编写程序的时候，预先写好捕获到 SIGTERM 信号时，需要做哪些退出前的清理工作。而 SIGKILL 则不能被捕获、忽略或者阻塞，SIGKILL 存在的目的是为了确保系统管理员可以拥有强制杀死某个进程的权力。

生产环境中通常先尝试正常停止（SIGTERM）；只有进程卡死或正常停止超时等情况下，才考虑强制终止（SIGKILL）。

SIGINT 指的是终端中断，在终端里按下 Ctrl+C 时，终端驱动会向当前前台进程组发送这个信号，通常用来请求程序"停下来"，信号是发给前台进程组，不只是某一个进程，所以管道 a | b | c 里的所有进程都会收到，后台进程（& 启动的）不会收到 Ctrl+C 产生的 SIGINT。

Web 服务对于退出的处理很重要，主要的原因是大部分的请求都不可能在一瞬间完成，特别是一些处理复杂的业务，可能需要耗时很久才能处理完，如果一视同仁的全部 kill -9（发送 SIGKILL 信号），那么很有可能业务逻辑执行到一半被强制终止推出了，一些重要的清理善后工作无法有效完成。

大部分的 Web 服务都支持优雅关闭（graceful shutdown），一般过程是：先停止接收新的请求，等待那些已经在处理请求的完成（但是会有超时时间），做好清理工作（数据库连接，文件句柄），最后停止进程。
